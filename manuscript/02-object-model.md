## 2.1 この章の目的

第1章では12の差分のうち4項目（インデント・代入・真偽判定と`None`・
型ヒント）を短いコードで先行体験した。この章はそのうち型ヒントを
除いた3項目を出発点に、Pythonの「構文の外形」（見た目のルール）と
「オブジェクトモデル」（値がどう扱われるか）を体系立てて扱う。

なぜこの2つを1つの章にまとめるのか。他言語経験者がPythonでもっとも
消耗するのは、文法エラーそのものよりも「エラーにならずに動くのに、
期待と違う結果になる」場面である。そしてその原因の大半は、構文が
やわらかい（`{}`もセミコロンも省略できる）ことと、代入の意味が

リストを共有してしまうバグは防げない。逆に代入の意味だけを知っても、
インデントの深さがずれたコードは実行前に落ちる。両方をセットで
押さえることで、「動くコード」と「意図通りに動くコード」の距離を
縮めるのが本章の狙いである。

本章のコード例はすべて`code/ch02/`に実体があり、`pytest`でその場で
検証できる。掲載する出力・例外メッセージは、対象バージョンである

## 2.2 インデントは構文である（深さの比較とタブ・スペース混在）

第1章1.3節では、字下げが1行だけずれたコードが`IndentationError`に
なることを確認した。ここでは一歩踏み込み、**タブとスペースが
混在したときに何が起きるか**を見る。

C系言語・JavaScript・Rubyでは、インデントに何を使おうと構文上の
意味はない。タブ2つでもスペース4つでも、字下げの「深さ」を比較する
処理系側の仕組みがそもそも存在しないからだ。Pythonは逆で、字句解析
の段階でインデントの深さをINDENT／DEDENTという専用のトークンに
変換する。深さの比較にタブとスペースが混ざると、この変換が一意に
決まらなくなる場合がある。

```python
def build_tab_space_mixed_source() -> str:
    """タブとスペースが混在した字下げのソースコード文字列を返す。"""
    return (
        "def f():\n"
        "\tprint('a')\n"
        "        print('b')\n"
    )


def compile_snippet(source: str):
    """文字列をコンパイルする（実行はしない）。"""
    return compile(source, "<snippet>", "exec")
```

```pycon
>>> compile_snippet(build_tab_space_mixed_source())
TabError: inconsistent use of tabs and spaces in indentation (<snippet>, line 3)
```

1行目の`print('a')`はタブ1つで、2行目の`print('b')`はスペース8個で
字下げされている。見た目の桁位置はエディタの設定次第でどちらとも
解釈できてしまうため、Pythonは`IndentationError`のサブクラスである
`TabError`を送出して実行前に止める。他言語であれば「読みにくいが
動くコード」で済む差異が、Pythonでは構文エラーになる。実務での対処
は単純で、**タブとスペースを1つのプロジェクト内で混在させない**
（多くのエディタ設定・`.editorconfig`・linterでスペース4個に統一
する）ことに尽きる。

インデントに関連してもう1つ、他言語経験者が驚く挙動がある。丸括弧・
角括弧・波括弧の**内側では改行がそのまま式の継続として扱われる**、
いわゆる暗黙の行継続である。

```python
def sum_across_continued_lines(
    first: int, second: int, third: int
) -> int:
    """丸括弧内での暗黙の行継続を使い、複数行にまたがる式を1つ返す。"""
    return (
        first
        + second
        + third
    )
```

```pycon
>>> sum_across_continued_lines(4, 5, 6)
15
```

C系言語ではセミコロンが文の終端を、Pythonでは改行が文の終端を表す
のが原則だが、丸括弧に囲まれている間はこの原則が一時停止する。
バックスラッシュ（`\`）による明示的な行継続も存在するが、末尾の
空白1文字で意味が壊れる（バックスラッシュの直後に空白があると
継続として認識されない）ため、実務では丸括弧を使った暗黙の継続が
好まれる。

## 2.3 代入は式ではなく文である

C系言語・JavaScriptでは、代入`x = 5`は値`5`を返す**式**であるため、
`if (x = 5) { ... }`のように条件式の中に埋め込める（多くの場合、
`==`の書き間違いを検出するために静的解析やlintで警告される書き方
ではある）。Pythonの`=`は値を返さない**文**専用の構文であり、
そもそも式が来るべき位置には書けない。

```python
def build_assignment_in_condition_source() -> str:
    """if文の条件式に単純代入 `=` を書いたソースコード文字列を返す。"""
    return (
        "x = 1\n"
        "if x = 5:\n"
        "    pass\n"
    )
```

```pycon
>>> compile_snippet(build_assignment_in_condition_source())
SyntaxError: invalid syntax. Maybe you meant '==' or ':=' instead of '='? (<snippet>, line 2)
```

エラーメッセージ自体が「`==`か`:=`の間違いでは」と提案してくる点に
注目してほしい。これは値を束縛しながら式としても使いたい需要が
実際に多かったことの表れで、Python 3.8で**海象演算子**（walrus
operator）`:=`が導入された。`:=`は代入と違って式であり、値を返す。

```python
def evaluate_with_walrus(x: int) -> int | None:
    """海象演算子で束縛した値を条件式の中でそのまま使う。"""
    if (doubled := x * 2) > 10:
        return doubled
    return None
```

```pycon
>>> evaluate_with_walrus(6)
12
>>> evaluate_with_walrus(3)
None
```

`doubled := x * 2`は「`x * 2`を計算し、その結果を`doubled`という
名前に束縛しつつ、式全体の値としても返す」という意味になる。単純な
`=`と`:=`は別物であり、通常の代入をこの形に置き換える必要はない。
「計算結果を条件判定にも使い、かつ後続の処理でも再利用したい」場合
にだけ使う、限定用途の構文だと理解しておけば十分である。

## 2.4 真偽判定は`__bool__`・`__len__`のプロトコルに従う

第1章1.5節では、`0`・空文字列・空リスト・`None`がfalsyとして扱われる
ことを組み込み型で確認した。ここで押さえておきたいのは、**この
判定は特別なハードコードではなく、`__bool__`・`__len__`という
プロトコル（お約束のメソッド名）に従っている**という点である。

`if obj:`が評価されるとき、Pythonはまず`obj.__bool__()`を探し、
それが定義されていなければ`obj.__len__()`を探し、要素数が0なら
`False`、そうでなければ`True`とみなす。どちらも定義されていない
オブジェクトは、常に`True`として扱われる。

```python
class SizedContainer:
    """`__len__`だけを実装し、要素数0のときfalsyになるクラス。"""

    def __init__(self, size: int) -> None:
        self._size = size

    def __len__(self) -> int:
        return self._size


class AlwaysTruthy:
    """`__len__`も`__bool__`も持たないため、常にtruthyになるクラス。"""
```

```pycon
>>> bool(SizedContainer(0))
False
>>> bool(SizedContainer(3))
True
>>> bool(AlwaysTruthy())
True
```

Javaの`if (obj != null)`やC#の同種の書き方に慣れていると、
「参照がnull（Pythonでいう`None`）でなければ真」という単純な規則を
期待しがちである。Pythonでは、たとえ`None`でなくても、`__len__`が
0を返す自作クラスのインスタンスは`if obj:`でfalse扱いになる。
list・dict・str・tupleのようなコレクション型が「空なら偽」に
なるのは、この`__len__`プロトコルの結果にすぎない。自作クラスに
「空かどうか」の概念があるなら、`__len__`か`__bool__`を実装する
ことで、組み込み型と同じ書き味の`if`判定を提供できる。

## 2.5 `None`は唯一のシングルトンである

JavaScriptには`undefined`と`null`の2種類の「値がない」表現があり、
Goにはゼロ値（型ごとに異なる既定値）がある。Pythonの`None`は
**プログラム全体でただ1つだけ存在するオブジェクト**であり、
`NoneType`という型のインスタンスは`None`しか作られない。

```python
def get_none_identity_pair() -> tuple[int, int]:
    """`None`の`id()`を2回取得し、そのペアを返す。"""
    return id(None), id(None)
```

```pycon
>>> get_none_identity_pair()
(109147745233600, 109147745233600)
```

`id()`が返す実際の数値は実行環境・実行のたびに変わるため、この値
そのものに意味はない。重要なのは2回の`id()`の呼び出し結果が完全に
一致していることで、これは`None`が呼び出しの間で1つのオブジェクト
のまま存在し続けている証拠になる。テスト側でも数値そのものではなく
2つの`id()`が一致することだけを検証している
（`code/ch02/test_ch02.py`の`test_none_is_a_stable_singleton`）。

この「唯一性」があるからこそ、「値が省略された」ことを表す
デフォルト引数には`None`を使い、比較には`==`ではなく`is`を使うのが
Pythonの慣用になっている。

```python
def greet(name: str | None = None) -> str:
    """`name`が省略（`None`）なら既定の挨拶にする。"""
    if name is None:
        name = "world"
    return f"hello, {name}"
```

```pycon
>>> greet(None)
'hello, world'
>>> greet("Python")
'hello, Python'
```

`is None`を使う理由は単なる慣習ではない。`None`は唯一のオブジェクト
であるため、「`None`と同一かどうか」を尋ねる`is`のほうが、値の
等価性を尋ねる`==`よりも直接的で、かつ`__eq__`をオーバーライドした
クラス（2.7節で扱う）の影響も受けない。

## 2.6 代入は名前の束縛である——連鎖代入と累算代入で見える実態

第1章1.4節では、`alias = origin`のような単純な代入によって同じ
リストが2つの名前から見えることを確認した。ここでは代入の実態を
さらに2つの角度から確認する。

1つ目は**連鎖代入**である。`a = b = c = []`は、1つの空リストを
生成し、その1つのオブジェクトへ`a`・`b`・`c`という3つの名前を
同時に束縛する。

```python
def bind_same_list_to_three_names() -> tuple[list, list, list]:
    """連鎖代入で3つの名前を同じ空listに束縛して返す。"""
    a = b = c = []
    return a, b, c
```

```pycon
>>> a, b, c = bind_same_list_to_three_names()
>>> a is b, b is c
(True, True)
>>> a.append(1)
>>> b
[1]
>>> c
[1]
```

`a`を経由して追加した要素が`b`・`c`からも見える。3つとも「同じ
オブジェクトを指す3つの名札」にすぎないからである。

2つ目は**累算代入**（`+=`など）である。ここで重要なのは、`+=`が
「常にその場で書き換える」わけではないという点だ。挙動は対象が
可変か不変かで分かれる。

```python
def increment_and_track_identity(value: int) -> tuple[int, bool]:
    """intへの`+=`前後で`id()`が変わることを確認する。"""
    before_id = id(value)
    value += 1
    after_id = id(value)
    return value, before_id == after_id


def append_and_track_identity(
    items: list, value: object
) -> tuple[list, bool]:
    """listへの`+=`前後で`id()`が変わらないことを確認する。"""
    before_id = id(items)
    items += [value]
    after_id = id(items)
    return items, before_id == after_id
```

```pycon
>>> increment_and_track_identity(10)
(11, False)
>>> append_and_track_identity([1, 2], 3)
([1, 2, 3], True)
```

`int`は不変オブジェクトなので、`value += 1`は「既存の`10`を書き換える」
のではなく「`11`という新しいintオブジェクトを作り、`value`という
名前をそちらへ再束縛する」動作になる。`id()`が変わるのはそのためだ。
一方、`list`は可変オブジェクトなので、`items += [value]`は
`items.extend([value])`とほぼ同じ意味になり、既存のオブジェクトを
その場で書き換える。`id()`が変わらないのはそのためである。「`+=`は
1つの演算子だから常に同じ動作」という前提は、Pythonでは成立しない。
**不変オブジェクトへの`+=`は再束縛、可変オブジェクトへの`+=`は
その場での変更**、という区別が、次節以降で扱う「参照セマンティクス」
と「可変・不変」の橋渡しになる。

## 2.7 引数渡しは「オブジェクトの共有渡し」

C系言語には「値渡し」と「参照渡し」という明確な区別があり、
JavaScriptでは「プリミティブは値渡し、オブジェクトは参照の値渡し」
という説明がよくされる。Pythonの引数渡しはこれらのどれとも厳密には
一致せず、**call by object sharing**（オブジェクトの共有渡し）と
呼ばれることが多い。実体は単純で、「仮引数という名前に、呼び出し元
と同じオブジェクトを束縛する」だけである。2.6節の区別がそのまま
関数呼び出しにも当てはまる。

```python
def rebind_only(value: int) -> int:
    """仮引数を新しいintへ再束縛するだけで、呼び出し元には影響しない。"""
    value = value + 1
    return value


def mutate_in_place(values: list) -> None:
    """同じlistオブジェクトを変更するため、呼び出し元にも影響する。"""
    values.append(99)
```

```pycon
>>> x = 5
>>> rebind_only(x)
6
>>> x
5
>>> items = [1, 2]
>>> mutate_in_place(items)
>>> items
[1, 2, 99]
```

`rebind_only`の中で`value = value + 1`をしても、それは仮引数`value`
という名前を新しいintオブジェクトへ**再束縛**しているだけであり、
呼び出し元の`x`が指すオブジェクトには何の影響もない。対して
`mutate_in_place`は仮引数`values`が指す**同じ**listオブジェクトに
対して`.append()`を呼んでいるため、呼び出し元の`items`からも変更が
見える。「関数に渡したら値が変わってしまった」という他言語経験者の
典型的な戸惑いは、ほぼ必ずこの「再束縛か、変更か」の見分けが
ついていないことに起因する。見分け方は単純で、**仮引数に`=`で
新しい値を代入しているだけなら影響しない。仮引数が指すオブジェクト
自身のメソッド（`.append()`・`.sort()`・`[i] = ...`など）を呼んで
いるなら影響する**、と覚えておけばよい。

## 2.8 `is`と`==`——そして小さいintのキャッシュ

`==`は「値が等しいか」を、`is`は「同一のオブジェクトか」を尋ねる。
第1章1.5節では`None is None`が`True`、`None == False`が`False`に
なることを確認した。ここでは`is`が持つ、もう1つの罠を確認する。

CPython（Pythonの標準的な実装）は、-5から256までの小さい整数を
起動時にあらかじめ生成してキャッシュし、使い回す最適化を行っている。
この範囲の整数は、別々の場所で生成しても`is`で比較すると`True`に
なることがある。ただし**これは言語仕様ではなくCPythonの実装詳細**
であり、他の実装や将来のバージョンで保証された挙動ではない。

同一のソース文字列内に同じリテラルを2回書くと、コンパイラの定数
畳み込みによって最初から同じオブジェクトが再利用されてしまい、
実装詳細としてのキャッシュを正しく実演できない。そこで、次のコード
ではあえて2つの独立した名前空間でそれぞれ`exec()`し、コンパイル単位
を分離した上で比較する。

```python
def create_two_ints_via_separate_compilations(
    value: int,
) -> tuple[int, int]:
    """同じ整数値を、独立した2つのコンパイル単位でそれぞれ生成する。"""
    namespace_a: dict = {}
    namespace_b: dict = {}
    source = f"result = {value}"
    exec(compile(source, "<ns_a>", "exec"), namespace_a)
    exec(compile(source, "<ns_b>", "exec"), namespace_b)
    return namespace_a["result"], namespace_b["result"]
```

```pycon
>>> a, b = create_two_ints_via_separate_compilations(200)
>>> a is b
True
>>> c, d = create_two_ints_via_separate_compilations(257)
>>> c is d
False
```

`200`は-5〜256の範囲に収まるためキャッシュされ、独立にコンパイル
しても同じオブジェクトが返って`is`は`True`になる。`257`は範囲外
なので、別々に生成された時点で別オブジェクトになり`is`は`False`に
なる。実務上の教訓は明快で、**intやstrの比較には常に`==`を使い、
`is`は`None`・`True`・`False`のようなシングルトンとの比較にだけ
使う**。「小さい数字なら`is`でも動くことがある」という事実は、
バグの温床にしかならない。

もう1つ、`is`と`==`が乖離する経路として、`__eq__`の独自定義がある。

```python
class AlwaysEqual:
    """`__eq__`を常にTrueへ固定し、`==`と`is`を意図的に乖離させるクラス。"""

    def __eq__(self, other: object) -> bool:
        return True
```

```pycon
>>> left = AlwaysEqual()
>>> right = AlwaysEqual()
>>> left == right
True
>>> left is right
False
```

`==`はクラスが`__eq__`をどう実装するかに完全に委ねられており、
「等しいと判定する条件」を自由に設計できる。一方`is`はオブジェクト
の同一性という、実装に左右されない事実を尋ねる。両者は独立した
質問であるという理解が、2.9節の「不変」の議論にもつながる。

## 2.9 不変は「浅い」——tupleと、浅いコピー・深いコピー

`tuple`は不変（immutable）なシーケンスだとよく説明されるが、この
「不変」は**要素の差し替えを許さない**という意味であり、要素として
持っているオブジェクトの中身までは保証しない。

```python
def build_point_with_mutable_tail() -> tuple:
    """1つ目がint、2つ目がlistの2要素tupleを返す。"""
    return (1, [2, 3])


def reassign_first_element(point: tuple, value: object) -> tuple:
    """tupleの要素を差し替えようとする（失敗しTypeErrorになる）。"""
    point[0] = value
    return point


def append_to_tail(point: tuple, value: object) -> tuple:
    """tuple自体は変えず、2つ目の要素であるlistへ追加する。"""
    point[1].append(value)
    return point
```

```pycon
>>> point = build_point_with_mutable_tail()
>>> reassign_first_element(point, 99)
TypeError: 'tuple' object does not support item assignment
>>> append_to_tail(point, 4)
(1, [2, 3, 4])
```

1つ目の要素（int）を差し替えようとすると`TypeError`になる。tuple
自身が「このインデックスにはこのオブジェクト」という対応関係を
変更させないからだ。ところが2つ目の要素であるlistは可変オブジェクト
なので、`.append()`で中身を変更でき、tuple越しに見た結果も変わる。
**「不変」は再帰的な保証ではない**、と覚えておく必要がある。

この「浅さ」は、コピーの話にも直結する。第1章1.4節で予告した
浅いコピーと深いコピーの違いを、ここでまとめて確認する。

```python
import copy


def shallow_copy_nested_list(source: list) -> list:
    """最も外側のlistだけを複製する（内側のlistは共有される）。"""
    return copy.copy(source)


def deep_copy_nested_list(source: list) -> list:
    """入れ子のlistまで再帰的に複製する。"""
    return copy.deepcopy(source)
```

```pycon
>>> original = [[1, 2], [3, 4]]
>>> shallow = shallow_copy_nested_list(original)
>>> deep = deep_copy_nested_list(original)
>>> original[0].append("shared")
>>> shallow[0]
[1, 2, 'shared']
>>> deep[0]
[1, 2]
```

`copy.copy()`（浅いコピー）は、一番外側のlistだけを新しく作り、
内側の`[1, 2]`・`[3, 4]`というlistオブジェクト自体は複製しない。
そのため、元の`original[0]`に対する変更が、コピーしたはずの
`shallow[0]`にも現れてしまう。`copy.deepcopy()`（深いコピー）は
入れ子になったオブジェクトまで再帰的に複製するため、元との共有が
断ち切られ、`original`側の変更は`deep`に影響しない。tupleの
「浅い不変性」とlistの「浅いコピー」は、根っこにある考え方が同じ
である。**Pythonのコピー操作は、明示的に指示しない限り、既定では
中身まで複製しない**。

## 2.11 なぜPythonはこう設計されたか

ここまでの8つの差分は、バラバラな仕様の寄せ集めに見えるかもしれない。
しかし裏側には一貫した設計判断がある。それは、**Pythonにおける
「変数」は値を格納する箱ではなく、オブジェクトに貼るラベルである**
という一点である。

C・Java・Go・Rustのような言語では、変数は型に応じた大きさのメモリ
領域そのものであり、代入はその領域へ値を書き込む操作になる。だから
こそGo・Rustは「値渡し」と「参照渡し」を明確に区別し、Rustはさらに
所有権によって「誰がその領域を書き換えてよいか」までコンパイル時に
決定する。Pythonの変数はメモリ領域ではなく、ヒープ上に存在する
オブジェクトを指す名前（ラベル）にすぎない。だからこそ代入は
「値のコピー」ではなく「ラベルの貼り替え」になり、複数の名前が
同じオブジェクトを指すことも、ラベルを剥がして別のオブジェクトに
貼り直すことも自由にできる。

この設計は、Pythonが**動的型付け・参照カウントによるガベージ
コレクション・「すべての値はオブジェクト」という統一されたモデル**
を採用したことの帰結である。型ごとに異なるメモリレイアウトを
コンパイル時に決め打ちする必要がないぶん実行速度では譲歩するが、
その代わりに「あらゆる値は名前を介してオブジェクトを指すだけ」
という単純な規則1つで、代入・関数呼び出し・コンテナへの格納の
すべてを説明できるようになる。可変・不変の区別が重要になるのも、
この統一モデルの帰結である。「ラベルを貼り替える」操作と
「ラベルの先のオブジェクトを書き換える」操作は別物であり、
オブジェクトが不変ならそもそも書き換える手段がないため、
共有されていても安全である。逆に可変オブジェクトを共有すると、
一方の変更が他方からも見えてしまう。

Go・Rustのように明示的な参照・借用・所有権を好む読者（本書のP4）
にとって、この「暗黙の共有」は不安の種になりやすい。しかし
Pythonの設計判断は「危険を隠す」ことではなく、「危険の所在を
可変・不変という1つの軸に集約する」ことにある。オブジェクトが
不変であれば、何人と共有しようと安全であることが保証される。
可変であれば、共有には注意が要る。この軸さえ意識すれば、`is`と
`==`の使い分け、tupleの浅い不変性、浅いコピーと深いコピーの違い
は、すべて同じ1つの原則から導かれる派生形にすぎない。次章以降で
list・dict・setの使い分けや関数のデフォルト引数の罠を扱う際、
この軸に何度も立ち返ることになる。
